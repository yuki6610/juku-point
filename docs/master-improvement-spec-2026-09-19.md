## 最優先原則

- 運用中の既存データと既存機能を壊さない。
- コード、Firestore構造、保存・読取処理、依存関係を確認してから変更する。
- 同じ業務データを画面ごとに独立保存せず、1つの正本と必要最小限の派生データを参照する。
- 管理者・講師で共通する型、検証、保存処理を共通化する。
- 破壊的DB変更や大規模リファクタリングは、影響と移行・ロールバック方法を確認してから行う。
- 管理者はPC向け高効率UI、講師・生徒・保護者はスマホ向けUIとする。
- 各段階で旧形式の読取を維持し、移行完了が確認できるまで旧データを削除しない。

## 実装段階

### 第1段階: Phase 1〜3

#### Phase 1: 既存不具合・データ互換性

- 交換履歴、自習中確認、振替管理、サイドバー遷移を調査・修正する。
- 志望校判定の単語テスト平均を選択学期の正しい集計にする。
- 講師画面で前回宿題選択時にスマホ表示が縮小しないようにする。
- 保護者招待を「URLを開く→本人登録→生徒紐付け→ログイン」まで成立させる。
- 招待URLに `0.0.0.0:8080` 等の内部URLを使用しない。
- 講師は招待URLを使わず、本人がアカウントを作成し、教室側が権限を承認する方式にする。
- 生徒用ログイン画面から「管理者」の表示を除く。
- 旧形式と新形式を併読し、既存データがあるのに表示されない状態をなくす。

#### Phase 2: 年度・学期・カレンダー基盤

- 管理画面の新規入力は、共通設定の現在年度・現在学期を初期値にする。
- 必要な画面では年度・学期を手動変更できるようにする。
- 学習記録の編集項目は新規登録項目と原則同一にし、年度・学期も編集可能にする。
- 授業カレンダーは年度ドキュメント方式を継続し、2027年度以降もコード変更なしで追加できるようにする。

#### Phase 3: 既存ページの役割整理

- 学習記録へ、小中高の出席、出欠確認、照合、振替記録の変更・削除を統合する。
- 設定へ、生徒曜日設定と授業設定を統合する。
- 教室授業設定は機能別タブにする。
- 一覧には用途に応じて学年・生徒・年度・学期・状態フィルタを設ける。
- 統合後も旧URLは当面リダイレクトまたは案内として残し、ブックマークを壊さない。

### 第2段階: Phase 4〜9

#### Phase 4: 小中高共通の学習記録

- 小学生: 出席・宿題。単語テストとテスト保存はなし。
- 中学生: 出席・宿題・単語テスト・成績。
- 高校生: 原則出席のみ。宿題・単語テストなし。保護者画面対象外。
- 校種ごとの対象外機能は表示しない。

#### Phase 5: 宿題管理

- 宿題は固定セットではなく1件ずつ保存し、各宿題を提出・途中・未提出で確認する。
- 複数宿題は、すべて提出で加点、1件でも未提出で減点する既存方針に対応する。
- 登録日と確認日を保存し、確認日は登録日+1週間を初期値にして変更可能とする。
- 教材は小学生・中学生別、教科別に絞り、管理者が表示順を変更できるようにする。

#### Phase 6: 単語テスト

- 宿題とは別データとして中学生だけを対象にする。
- 範囲はページではなく番号で管理し、生徒ごとの現在範囲を保持する。
- 次回は「同じ範囲」または「次の範囲」を実番号付きで選択する。

#### Phase 7: 授業中入力

- 授業開始時の前回宿題・単語テストと、授業終了時の次回宿題・評価・保護者向け情報を分けて入力できる設計にする。
- 一時保存または2段階保存を、スマホ操作数と未完了管理を比較して決定する。

#### Phase 8: 講師画面

- 管理者と同じ学習記録データ・保存ロジックを使う。
- スマホ向けに前回宿題選択を簡潔にする。
- 生徒別の授業方針メモと使用教材を表示する。

#### Phase 9: 保護者向け授業レポート

- AI/APIを使わず、講師が選ぶ事実・評価と既存記録を条件分岐で文章化する。
- 価値の高い2〜3項目を中心に自然な文章を生成し、プレビュー後に保存する。
- 特記事項だけ自由記述を許可し、将来の前回比較に拡張できる構造にする。

### 第3段階: Phase 10〜13

- Phase 10 生徒メモ: 学年フィルタ、増減に強い一覧、模試欄削除、編集対応、氏名・学年の視認性向上。
- Phase 11 成績・学期レポート: 管理者と生徒のテスト仕様統一、授業実施に欠席を含め、学習態度から欠席とバー表示を除く。
- Phase 12 保護者ホーム: 要確認、本人の次回授業、次回宿題、直近授業、最近の成績、お知らせの順で表示する。中学生・中3・小学生の表示差を守る。
- Phase 13 保護者授業記録: 直近優先、月・期間整理、過去折りたたみ。独立宿題欄を廃止し、宿題詳細は授業記録内、次回分はホームに表示する。

### 第4段階: Phase 14〜15

- Phase 14 保護者カレンダー: 営業日、通常・振替・講習授業、学校・教室イベント、面談、入試、宿題確認日等を統合する。既存データから取得できる予定は二重入力しない。対象は全員・学年・学校・個人を指定可能にする。
- Phase 15 お知らせ・PDF: 別データとして個別保存・編集・削除する。お知らせテンプレートと対象配信を用意する。PDFは資料タブに残し、校種別・カテゴリ階層・スマホ閲覧を前提にする。

### 第5段階: Phase 16〜19

- Phase 16 講習申込: 固定コースと回数選択型、単価×コマ数、最終確認を実装する。申込後訂正方式は既存構造を調査して提案後に決定する。
- Phase 17 講習日程: 不可時間入力、管理者配置、配置数・同時人数表示、保護者確認、変更依頼、確定の状態管理を行う。確定分はカレンダーへ反映する。
- Phase 18 講習宿題進捗: 講習予定・宿題・毎週の進捗を関連付ける。
- Phase 19 面談予約: 管理者が枠を設定し、保護者が予約する。Firestoreトランザクション等で同時予約を排他制御し、確定分をカレンダーへ反映する。

### 第6段階: Phase 20〜21

- Phase 20 友人紹介: 案件単位で申込から商品券付与済みまで管理し、入会2か月後を付与予定日にする。回数制限なし。
- Phase 21 高校情報: 通学時間・部活動等を追加し、項目追加に耐える構造にする。

## データ設計ルール

- 正本、派生集計、公開用投影、旧形式を区別する。
- `lessonPublic` や `homeworkPublic` のような権限制御用投影は正本ではなく、サーバー保存処理から同時更新する。
- 派生集計は元記録から再構築できるようにする。
- 旧形式は読取互換だけを維持し、新規保存先は1つに固定する。
- すべての変更に `createdBy`、`updatedBy`、`createdAt`、`updatedAt` を可能な範囲で持たせる。
- 移行は「互換読取追加→新規書込統一→検証→任意バックフィル→旧読取廃止」の順にする。
