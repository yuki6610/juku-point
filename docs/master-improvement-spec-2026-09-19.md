# 新規実装・機能追加

## 13. 生徒・保護者AIアシスタント
標準モデルはGPT-6 Luna。テキストのみ。
【生徒】今日の宿題／次回授業／カレンダー／数学・英語などの質問／宿題の解き方
学習質問は、ヒント → 考え方 → 解説 → 必要なら答えの順。
生徒の通常の質問はGPT-6 Lunaで回答する。GPT-6 Solは、希望する生徒がその質問に限って選べる追加オプションとし、1回500ptを消費する。Solを自動選択したり、通常のLuna回答を置き換えたりしない。Solは複雑な問題の考え方や複数の解法の比較などで利用する選択肢とし、Solの方が必ず正答するとは案内しない。
質問内容が不十分な場合は、回答前に「問題文」「自分で試したこと」「どこから分からないか」を入力しやすい形で補助する。不足情報だけ1〜2問確認し、整えた質問を本人に表示する。この補助段階では500ptとSol利用枠を消費しない。
質問が整った後に、通常の「Lunaで質問する」と追加の「Solで質問する（500pt）」を並べ、本人が選択・確認する。Solの回答生成に失敗した場合はポイントとSol利用枠を消費しない。回答の品質に問題がある場合は報告できるようにし、ポイント返還は管理者が個別に確認する。
【保護者】今日営業しているか／次回授業／宿題／面談／講習／お知らせ／最近の授業状況など。
生徒画面と保護者画面に、それぞれの利用者向けのAIアシスタントを表示する。
保護者AIは、閲覧権限のある子どもの授業・宿題・成績・面談・お知らせ・登録済みの進路情報を参照できる。他の家庭の情報は参照しない。学習状況を回答に使うときは、その学期中の記録と前学期の承認済みレポートに絞る。生徒AIも同じ期間の学習情報を参照する。
会話履歴はDBに保存し、利用者が自分の過去の会話を見られるようにする。保存期間は最終発言から180日とし、期限到来時に会話本文を削除する。
管理者は教室運営上の必要がある場合だけ個別会話を閲覧でき、閲覧理由・閲覧者・日時を記録する。一覧での一括閲覧・検索は設けない。利用者には管理者が閲覧できることと保存期間を事前に明示する。DB管理権限を持つ運営者はDB上の本文を閲覧し得るため、DB権限は必要な担当者に限定する。

## 14. AIを使わない質問
Firestoreから直接答えられる、営業状況／次回授業／今日の宿題／面談期限／講習期限／所持ポイントなどではLunaを呼ばない。
AIを使うのは、学習解説／要約／複数データの分析／自然文章作成など。

## 15. AI利用方針と乱用対策
通常のLuna質問に、5時間・週間・月間などの固定回数制限やポイント消費は設けない。Solは生徒が希望する質問だけ1回500ptを消費する。
無意味な大量送信や自動連打を防ぐため、同一利用者の同時生成は1件までとし、同じ質問の連続送信を抑制する。入力・出力の長さと会話履歴として送る量に上限を設けるが、通常の学習相談を回数で止めない。
用途別のAPI利用量・費用を記録し、急増時には管理者へ通知する。異常な利用は管理者が確認し、必要な場合だけ個別対応する。通常利用者に対する自動的な日次・週次の利用停止は行わない。
費用急増や障害に備え、管理者がAI生成を一時停止できる緊急停止機能を設ける。停止中は利用者に理由を表示し、Sol質問のポイントは消費しない。警告・停止の具体的な金額閾値は運用開始前に決める。

## 16. AIバグ報告
生徒・保護者はAIアシスタントに自然文でバグ報告できる。
例：「宿題が表示されない」
AIは不足情報だけ1〜2問確認する。
自動取得候補：日時／ユーザー／role／現在ページ／端末・ブラウザ／アプリバージョン／エラー情報
ユーザー確認後にバグDBへ登録する。
状態：未確認／確認済み／対応中／対応済み
バグ報告は通常の質問とは別の導線で扱い、Solの500ptは消費しない。

## 34. 学期レポート

中学生のみ対象。保護者画面では、承認済みの学期レポートだけを表示する。
管理画面では、学期途中でも現時点までのデータを使った総括を下書きとして生成・編集・表示・印刷でき、面談資料に利用できる。この下書きは承認するまで保護者に公開しない。
管理者ページに独立した「学期レポート管理」を作る。

状態例：未生成／AI生成済み／承認済み／要再生成。
対象生徒を一括生成できる。承認済み生徒は一括生成対象から除外する。
フロー：AI生成 → 管理者編集 → 管理者承認 → 保護者公開。

承認時点の文章・集計値・グラフ用データを公開用スナップショットとして固定する。元データが後から増減しても公開内容は自動更新しない。更新するときは管理者が再生成または編集し、再承認する。

## 35. 学期レポートの役割

単なる成績表ではなく、「その学期の学習状況と成長をまとめるページ」とする。
数値やグラフはFirestore側で計算する。
元データがない項目は「データなし」と表示する。AIに数値や学習状況を推測・補完させない。
AIは、学期総括／成長／課題／次学期の指導方針などの文章のみ作成する。

## 36. 学期レポートに載せる情報

一旦すべて実装し、情報過多なら後から削る。

集計は既存記録から直接数えられる単純な方法にする。宿題提出率は「提出済み ÷（提出済み＋一部提出＋未提出）」とし、欠席で未確認・判定未入力は母数に入れない。一部提出は別件数として表示し、提出済みには数えない。単語テストの平均正答率は、実施したテストの「正解数合計 ÷ 問題数合計」とする。5段階評価は項目ごとに入力された値だけの単純平均とし、入力がなければ「データなし」。推移グラフは記録済みの値を時系列で示し、欠測値の補間や予測はしない。

- AI文章：学期総括／教科別の成長／できるようになったこと／今後の課題／課題の変化／次学期の指導方針
- 学習状況：宿題提出率／宿題提出率推移／単語テスト平均／単語テスト学期内推移／集中度・自力解決度・説明力／単元ごとの理解度・定着度
- 成績推移：定期テスト／実力テスト／内申点／校内推定偏差値

点数については単純な一覧として強調するのではなく、推移を見るデータとして使用する。

- 学習習慣：自習時間推移／自習回数推移
- 授業記録：予定授業数／実施授業数／出席／欠席／振替実施／残振替
- ランキング：自習時間／自習回数／単語テスト総得点
- 単元別の学習履歴：中学生の数学・英語で扱った単元、基礎・応用などの区分、単元ごとの理解度・定着度。記録がない単元の評価は推測しない

## 中学生の授業報告：単元と5段階評価（実装前に決定）

対象は中学生の数学・英語。国語・理科・社会には今回単元プルダウンを設けない。授業報告の教科を選ぶと、その教科と生徒の現在学年に対応する単元を最初に表示する。「他の学年を見る」で中1〜中3の候補へ切り替えられる。前学年の復習でも選べるようにし、選択中の教科から一日に複数単元を選べる。教科を変更したときは、異なる教科の単元を誤保存しないよう選択内容を確認する。

単元一覧は固定の教科書データではなく、管理者が教科・対象学年ごとに登録、編集、表示順変更、有効・無効の切替を行う。数学は計算などの「基礎」と文章題などの「応用」、英語は文法を中心とした分類を扱えるようにする。ただし、単元名から基礎・応用を自動決定せず、授業時に選んだ区分を記録する。集計は区分ごとの記録件数と評価の単純な推移に留め、件数だけで得意・不得意を断定しない。

5段階評価は次のように分ける。評価していない項目は未入力とし、0点や1点には換算しない。

| 評価の単位 | 項目 |
| --- | --- |
| 授業全体 | 集中度、自力解決度、説明力 |
| 選択した各単元 | 理解度、定着度 |

定着度は初回の授業など確認できない場合に入力を求めない。講師画面と管理者画面で同じ項目・保存形式を使う。現在の「学習態度」と管理者画面に残る「質問」は新しい入力・学期レポートの評価項目に含めず、既存記録があれば壊さずに残す。

記録には授業当時の学年、教科、単元IDと表示名、選択した区分、評価値を保存する。進級や管理者による単元名・順序の変更で過去の授業記録が書き換わらないようにする。既存の単元未登録の授業には推測で単元を補完しない。保護者の授業記録には選択した単元名を表示するが、5段階評価の生データは教室内のみで使用し、保護者には承認済みの文章やレポートで伝える。

### 講師の入力UI案（少ないタップ・短いスクロールを優先）

- 現在の授業報告欄は折りたたみ可能なままとし、開いたときは「教科 → 単元 → 評価 → 学習内容・文章」の順にまとめる。入力中の生徒名は既存どおり画面上部に固定する。
- 講師画面と管理者の授業入力画面は、選択日の**確定シフトを優先し、確定シフトがない場合だけ通塾曜日・時間・教科の設定へ戻る**同じ読み込みルールを使う。両画面の教科初期値が日付・生徒・シフト状態によって食い違わないようにする。教科は必要な場合だけ変更できる。選択済み単元がある状態で教科を変える場合は、古い教科の単元をそのまま保存しない。
- 単元の選択欄は最初は短く表示する。開くと現在学年の候補を管理者設定の順番で表示し、行を一度タップするだけで選択・解除できる。他学年は切替タブから開く。選択済み単元は本文側に短い一覧として残し、候補一覧を閉じても確認できる。
- 基礎・応用などの区分は選択済み単元の行で直接切り替えられるようにし、別ページを往復させない。区分を未設定のまま数値集計に含めない。
- 授業全体の3項目は、各行に1〜5のボタンを並べる。選択は1タップ、同じ値の再タップで解除。未入力を自動的に「3」としない。
- 選択した単元は一覧では「単元名・学年・区分・入力済み評価」を1行に要約する。評価を入力する単元だけ展開し、理解度・定着度を各1タップで選べる。新しく選んだ単元はその行を自動的に開き、複数単元でも全評価欄が常時縦に並ばないようにする。
- 既存の自動保存を維持し、単元や評価の選択にも適用する。保存状態とエラーはスクロール位置に関係なく分かるようにする。タップ領域はスマホで押しやすい大きさにし、色だけで選択状態を表さない。
- 管理者の単元設定では学年・教科ごとに並べ替え、無効化ができるようにする。無効化しても過去の授業記録の単元名は残す。

## 管理者AIアシスタント（追加提案・未実装）

### 役割と画面

管理画面に独立した「AIアシスタント」を置く。自由入力に加えて「教務」「生徒管理」「保護者対応」「販促」「経営・分析」の業務ボタンを設ける。初期版は、管理者が確認して使う文章・資料の**下書き作成まで**とする。AIによるDB更新、外部投稿、一斉送信、削除は初期実装に含めない。

| 販促・連絡の候補 | 最初に作るもの | 将来の拡張 |
| --- | --- | --- |
| GBP・SNS投稿、口コミ返信 | 投稿文・返信文、必要なら画像案 | 外部アカウント連携と管理者確認後の投稿 |
| ポスティング・講習案内 | 対象別の見出しと本文、チラシ構成案 | テンプレートへの配置、画像生成、PDF出力 |
| 保護者お知らせ、面談・休校案内 | アプリ掲載文やLINEに転記する文案 | 管理者確認後のアプリ内登録・配信 |
| 生徒募集・月間販促 | キャンペーン案、週ごとの企画案 | 実績・問い合わせ数との比較 |

例：「垂水中の中間テストまで2週間。GBP投稿案を作って」→確認できた学校行事・試験日程・講習情報を提示→文章と画像案を生成→管理者が編集・保存する。チラシは、文章・素材・固定テンプレートを組み合わせる案とし、画像1枚に日本語本文まで描かせることを前提にしない。画像生成とPDF化は別工程として扱う。

### 現在のデータとの接続

| 情報 | 現状の扱い |
| --- | --- |
| 授業、宿題、成績、自習、出欠、講習日程、保護者予定 | アプリ内に保存経路がある。管理者AIからの参照は用途ごとに必要最小限に限定する |
| 学校行事・定期テスト日程 | 一部の予定情報はあるが、学校別の販促用日程が網羅・更新される仕組みは未確認。未登録なら管理者入力を求める |
| キャンペーン、過去のGBP/SNS投稿、問い合わせ数、販促成果 | 現行アプリの標準データとしては確認できない。DB参照済みとして扱わず、登録画面・履歴・指標の設計が必要 |
| 塾の料金・実績・所在地など対外的な主張 | 公開してよい確定情報のみ管理者が登録・確認する。AIが数値や実績を作らない |

個人を特定できる生徒情報や保護者相談内容を販促文へ混ぜない。集計値を使う場合も、対象・期間・母数を表示して管理者が確認する。外部へ送る操作を追加する場合は、プレビューと明示的な最終確認を必須にする。

## ポイント交換で使うアバター・AIキャラクター（追加提案・未実装）

現在の生徒アバターはVRM/GLBファイルを本人が登録して表示する方式で、景品交換とポイント履歴は既にある。ポイント交換キャラクターは**生徒のプロフィール用アバターを主用途**とし、AIアシスタント画面でも同じキャラクターを使う。既存の持ち込みアバターは残す。候補素材が現在の3D表示方式で使えるか、別の表示方式が必要かは素材選定時に確認する。

初期案は無料キャラクター1体（例：Robot）と、ポイント交換で解放する複数の見た目（例：Chibi・Fox・Dragon）。AIの学習支援能力とモデル選択はキャラクターで変えない。Sol質問券の500ptとも別の商品として扱う。衣装・装備・進化・背景・エフェクトは将来案とし、初期版には含めない。

解放時はポイント残高の確認、減算、交換履歴、保有権の付与を同一の安全な処理で行い、二重交換を防ぐ。キャラクターの変更は再課金せず、保有権から選択する。既存の景品交換機能をそのまま流用できるかは、在庫・引渡しなど物理景品向けの項目を確認して決める。

素材候補（itch.io の styloo系、Gobkit、Sketchfabなど）は未選定。無料・商用利用可・軽量・できればアニメーション対応を条件とするが、**候補ごとのライセンス、再配布条件、改変可否、クレジット表記、形式、容量を確認するまで採用しない**。CC0であると仮定しない。

## AI構想などで次に決めること

実装順は、既存データを使う学習履歴の整理 → 学期レポート → 生徒・保護者AI → 管理者AI → ポイント交換アバターを基本とする。依存関係に応じた細部の前後は実装時に調整する。

1. 管理者AIが最初に参照する情報と、販促に必要な塾情報・日程・キャンペーンの登録方法。
2. ポイント交換アバターの価格、初期素材、3D表示方式との互換性。
3. 退塾生の完全削除時のバックアップからの消去方法と、削除前に管理者へ示す対象データの確認方法。
4. AI利用費の警告・緊急停止の具体的な金額閾値と、停止を解除できる管理者。

## 生徒・講師・授業運用の追加要件（未実装）

### 退塾生と保護者の利用停止・復帰・完全削除

- 生徒を「在籍／退塾」で管理する。退塾時は生徒本人と、その生徒にしか紐づかない保護者のアプリ利用を停止し、通常の生徒選択、シフト、授業報告、ランキング、通知対象などのUIから除外する。複数の子どもに紐づく保護者は、在籍中の子どもへのアクセスまで停止しない。
- 退塾状態では学習記録、ポイント、授業報告、成績、紐づけ情報を削除せず保持する。管理者には別の「退塾生」一覧を用意し、同じ生徒IDのまま在籍状態へ戻せるようにする。復帰時は保護者の紐づけとアクセスを再評価する。
- 管理者に完全削除機能も設ける。退塾・利用停止とは別操作にし、対象生徒と関連データの範囲を事前表示して二段階確認する。生徒の認証アカウント、授業・成績・ポイント・AI会話など対象生徒に属するデータも削除する。過去の承認済み記録も対象とし、画面から隠すだけで完了とは扱わない。
- 対象生徒だけに紐づく保護者アカウントも削除する。兄弟姉妹が残る場合は保護者アカウントと他の子どものデータを残し、削除対象生徒との紐づけだけを外す。共有記録を誤って消さないよう、削除対象を事前に確認する。バックアップからの消去手順は実装前に確認する。

### 講師アカウント削除

- 管理者が講師アカウントをメールアドレスとUIDで区別して一覧表示し、複数アカウントのうち不要な片方だけを削除できるようにする。同姓同名でも誤削除しないよう、確認画面にメールアドレスを明示する。
- 削除対象アカウントのログイン権限を止める。過去の授業報告の担当講師表示は消失させず、必要なら当時の講師名とメールアドレスを記録側に残す。担当シフトと未承認報告への影響を削除前に表示する。

### 授業報告承認・ランキング・テスト入力

- 管理者が生徒メモに登録した志望校を、担当講師の生徒情報にも表示する。対象は中学生・高校生のみとし、小学生には欄自体を表示しない。講師画面からは閲覧のみとし、編集元は管理者の生徒メモに統一する。
- 管理者の授業報告承認ページには、授業を担当した講師を表示する。承認ページは授業日と何講かで並べ替えられるようにし、少なくとも同日の報告は3講→7講の順に確認できるようにする。保護者向けの授業報告には担当講師を表示しない。
- 単語テストの点数がランキングに反映されない生徒がいるため、保存元、集計対象、学期判定、複数回テスト、欠席・振替、旧形式の記録、ランキング更新の経路を調査する。原因確定前に点数や順位を補正しない。
- 保護者または講師が「未提出のテスト」をタップして入力画面を開いた場合、そのテストの対象年度・学期・テスト種類を自動選択する。対象レコードを特定できない場合は推測で選ばず、選択を求める。

### 面談・お知らせ・保護者カレンダー・講習

- 管理者の面談可能日時設定では終了時刻を入力させず、開始時刻だけを登録する。面談時間は対象生徒が中学生なら60分、小学生・高校生なら30分とし、重複判定やカレンダー表示に必要な終了時刻は自動計算する。学年区分によって枠長が変わるため、同じ開始枠を異なる学年に公開する場合も予約の重複を防ぐ。
- お知らせの公開対象を自由入力させず、公開範囲を選ぶと該当する学年・タグ・生徒などの候補を自動表示する。対象選択から保存前までのプレビューを設け、誰に見えるかを確認できるようにする。
- 保護者対応ページのカレンダーも同じ対象選択とプレビューを使い、登録済みタグで表示対象を判定する。対象件数だけでなく、権限の範囲内で対象者を確認できるようにする。公開対象はタグによって動的に判定し、後から生徒のタグを変更したら既存のお知らせ・予定の表示対象も変わる。タグの変更頻度は低いため、過去分を固定する特別な仕組みは設けない。プレビューには現時点の対象を表示する。
- 講習申し込み設定には対象学年の選択を設ける。対象条件は学年だけとし、自由入力や生徒別指定は設けない。申し込み画面にも同じ対象判定を使う。
- 保護者が講習申し込み後に登録する「授業を受けられない日時」は、日付・開始・終了を1件ずつ手入力する方式を主にせず、面談日時設定と同じ日付×時間帯の表で選ぶ。講習期間の日付を列、固定の授業時間帯を行に並べ、受けられない枠をタップして選択・解除する。選択状態をまとめて確認して保存でき、既存の来校不可データへ反映する。面談予約の枠や予約状態とはDBを共有せず、表の操作方法だけ再利用する。
- 管理者の講習日程設定にも面談設定と同じ日付×時間帯の表形式を使う。講習期間を列、時間帯を行とし、枠を選んで生徒・教科・担当講師を割り当てる。表の操作部品は共通化しても、講習日程と面談予約のデータ・権限・状態は分ける。
- 保護者の不可日時提出を待たずに、管理者が講習日程を下書き配置できる。表には「未提出／提出済み」を生徒ごとに示し、提出後は該当生徒の不可時間を表に重ねて表示する。未提出は「予定なし」と同義にしない。**保護者の提出後にだけ日程を確定できる。**
- 今回の講習日程は既存の固定90分授業枠を使う。13:00〜19:00の過去問演習のような長時間授業を1回分として登録する機能は、複雑化するため実装対象から外す。

#### 保護者の不可日時を後から反映したときの確定挙動

1. 保護者が不可日時を提出・更新したら、同じ講習・生徒の下書きと確定済みの日程を固定授業枠の時刻で再照合する。重なりがなければ既存日程はそのまま残す。
2. 重なった日程は表と一覧に「要調整」と表示し、管理者へ確認を促す。自動移動・自動削除・別日時への自動確定は行わない。下書きのままなら、衝突を解消するまで確定とシフト反映を止める。
3. すでに確定済み、またはシフトへ反映済みの日程が衝突した場合も、保護者の提出を黙って捨てず、日程を黙って消さない。管理者が保護者へ確認してから、日程とシフトを整合的に変更・再確定する。衝突が残る間は「要調整」を明示する。
4. 保護者には管理者の下書きを公開せず、確定済み日程だけを表示する。提出した不可日時と確定済み日程が衝突したら、元の日時を保護者カレンダーから黙って消さず、「教室と調整中」と明示する。

上記を確定仕様とする。管理者の日程表と保護者の不可日時表は同じ固定授業枠を使用し、提出後の重複判定結果を確定操作とシフト反映に一貫して適用する。

### 講師のシフト希望タブ

- 表示順を「シフト希望表 → 指導可能科目」に変更する。指導可能科目は初回入力・送信後、次回から折りたたんで表示する。変更が必要なときだけ展開できる。
- 学年区分は小学生・中学生・高校生の3つとし、学年ごとに指導可能な教科を選ぶ。小学生は国語・算数・英語・理科・社会、中学生は国語・数学・英語・理科・社会。高校生は教科を細分化し、理科は物理基礎・化学基礎・生物基礎・地学基礎と、物理・化学・生物・地学を別々に選べるようにする。他の高校科目の最終一覧は実装前に確認する。
- 現在の講師希望データは全学年共通の教科配列と小1〜高3の学年配列なので、新形式への移行時に既存回答を失わない。管理者の講師割当画面も新しい学年別科目を参照する。

### 管理者の週シフトUI改善案

現状のシフトは、1授業につき生徒・教科・担当講師に加えて授業種別、曜日、時間帯などのプルダウンを常時表示するため、横幅と行高が大きい。PCで週全体を見渡せることを優先し、**表示と編集を分離する**。

| 表示状態 | UI案 |
| --- | --- |
| 週の一覧 | 月〜土を列、3〜7講を行とする。各枠は人数に応じて授業行を増減し、空の行を固定表示しない。曜日は列見出し、何講かは行見出しにだけ表示する。 |
| 1授業の表示 | コンパクトな「生徒名｜時間＋教科｜担当講師」の3セル横並び。通常時間は省略し、通常と異なる開始時刻だけ教科の前に表示する。終了時刻は表示・入力しない。生徒名は原則苗字、同姓が重なる場合は登録名の下の名前の漢字1文字目を付ける（田中太郎→田中太）。なお同じ表示になる場合は識別できるまで下の名前を増やす。詳細を開けば必ずフルネームを確認できる。 |
| 種別の識別 | 通常・振替・講習を淡い背景色で分け、色だけに依存しない小さな文字ラベルや凡例も付ける。 |
| 編集 | 授業行をクリックしたときだけサイドパネル等に生徒・教科・担当講師・授業種別・例外時刻・振替元・移動先を表示する。通常の表にはプルダウンを並べない。追加は対象枠の「＋」、削除は詳細画面から行う。 |
| 見通し | 週切替・保存状態・未割当講師件数を上部に固定し、列見出しと何講の行見出しをスクロール中も残す。画面幅が足りないときは読めない縮小を強制せず横スクロールする。 |

週シフトの確定・翌週コピー・講習反映・新規生徒反映の操作は維持する。見た目の短縮名は表示専用とし、保存は従来どおり生徒キー、授業日、講ID、教科コード、担当講師UID、授業種別、振替元などの識別子で行う。例外授業では開始時刻のみを扱い、授業時間は90分として終了時刻を自動算出する。講IDとの関係を明示し、授業報告、出欠、保護者カレンダー、講師割当が同じ授業を参照できるようにする。表示のために別のシフトDBを作らない。

実装前に確認する点：高校生の理科以外の科目一覧、完全削除とバックアップの扱い。通常時間と異なる授業の開始時刻が既存の講IDと一致しない場合の紐づけは、連携箇所を確認して設計する。
